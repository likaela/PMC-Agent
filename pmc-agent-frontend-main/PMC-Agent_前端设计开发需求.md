# PMC Agent 前端设计开发需求

**交付对象：** 负责前端产品设计与 Vibe Coding 的队友  
**用途：** 设计并实现一个可演示、可继续接入后端的制造业 PMC 智能工作台  
**依据：** 当前项目能力与既定 v1.9 至 v1.14 路线。具体接口字段和版本完成状态以交接时的仓库及接口样例为准。

## 1 项目目标

PMC Agent 服务于生产计划与物料控制场景。用户用自然语言提出生产或物料问题，系统查询已发布的企业事实，由后端完成确定性计算，再将结论、依据和数据来源呈现给用户。面向 PMC 计划员、生产主管和采购人员，核心问题是：能否生产、能生产多少、缺哪些料、何时可能到料、需要怎样处理。

请交付一套**可运行的 Vue 3 前端设计与代码**，让评委或企业用户在几分钟内理解项目价值并完成典型操作。界面应像企业工作台，突出可核查的业务结论，而非仅有聊天气泡。视觉设计可重新构思，但不能凭空制造后端尚未提供的计算结果。

## 2 能力边界与版本演进

| 阶段 | 前端需要呈现的能力 | 设计处理 |
| --- | --- | --- |
| 当前基线 v1.9.x | 智能对话、生产分析、库存与 BOM 等事实查询、产能查询、来源追溯；以实际接口为准 | 做成真实接口可接入的主流程，并提供空状态、错误状态与来源详情 |
| v1.10 | 多层 BOM、版本与生效期、单位换算、齐套和最大产能计算 | 预留 BOM 树、版本标识、计算明细；上线状态以真实接口为准 |
| v1.11 | 批次库存及库存可用性 | 预留批次明细、库位和不可用原因的展开区 |
| v1.12 | 缺料处置与采购建议 | 预留建议卡及其依据、约束和人工确认入口 |
| v1.13 | 企业知识问答等增强能力 | 预留知识引用区，明确区分知识回答与事实计算 |
| v1.14 | 比赛演示场景 | 固定演示入口和可复现操作路径，但不把模拟内容伪装成实时事实 |

上表描述的是**界面适配路线**，不代表每项后端能力现在已经交付。队友先以真实 API 样例核对当前字段；未来能力可制作标明“设计预览”的静态原型，不能以假数值进入正式结果区。

## 3 关键用户任务

1. **生产决策：** 输入产品、数量和必要条件；查看能否生产、齐套情况、缺料、风险及可采取的行动，并展开计算依据。
2. **事实查询：** 用料号或自然语言查询库存、BOM、在途等；查看数量、单位、状态、发布时间和来源。没有事实时明确显示“暂无已发布数据”，不要展示 0。
3. **最大产能：** 查询现有库存下的理论最大生产量，查看限制物料和计算前提；事实不足时提示无法计算。
4. **继续追问：** 在后端确实支持的会话语义范围内承接上下文；如果接口不支持上下文，界面要求用户补全产品或数量，不能自行拼造回答。
5. **数据追溯：** 从每个关键结论到物料、BOM 版本、库存来源、时间及告警，形成清晰可回看的路径。

## 4 页面与信息架构

### 4.1 首页

首屏说明产品是谁、解决什么问题，并提供“开始分析”入口。用三个可点击的场景卡引导：生产可行性、库存查询、最大产能。示例问题必须与演示数据匹配；如“我要生产 100 台 KQ-Z112”只有在该产品确有已发布事实和可运行流程时才作为一键发送示例，否则仅作输入提示。首页要有清晰的产品身份与可阅读的价值说明，避免堆砌概念图标。

### 4.2 智能工作台

桌面端建议左侧对话、右侧结果面板；窄屏改为上下布局或可切换页签。对话区包含示例提问、输入、发送中、失败重试、消息时间和可读的回答。结果区根据接口结果显示任务摘要、结论、关键指标、明细、来源和警告。切换历史消息时结果面板与对应回答同步，避免显示上一次计算。

### 4.3 结果组件

| 组件 | 必备信息 | 交互 |
| --- | --- | --- |
| 生产决策摘要 | 产品、目标数量、生产结论、数据状态 | 跳转到缺料与计算依据 |
| 齐套与缺料 | 齐套指标的定义、物料需求、可用量、缺口、单位 | 表格筛选和逐项展开；无数据时不绘制百分比 |
| BOM 结构 | 父子层级、用量、单位、版本、生效期及来源 | 展开、收起、定位物料；循环或冲突显示无法计算 |
| 库存与批次 | 物料、已发布库存、单位、批次或库位（若有） | 查看来源与批次明细 |
| 产能 | 理论最大数量、限制物料、计算条件 | 查看每项限制及其依据 |
| 采购建议 | 建议动作、缺口、约束、来源（接口支持后启用） | 明示建议性质与人工确认状态 |
| 来源与警告 | 文件或事实记录、版本、发布时间、警告 | 一键展开完整来源；字段缺失时如实显示 |

业务结论使用清楚的中文；技术细节可放在调试模式或开发文档中。表格长数据要可滚动，数字须保留单位和合理精度。图表必须对应后端提供且定义明确的指标。

### 4.4 状态设计

至少覆盖：欢迎、输入中、请求中、成功、部分数据可用、无已发布事实、条件冲突、无法计算、接口错误和重试。区分“库存为 0”“没有库存事实”“请求失败”。`warnings` 要可见，不得被卡片布局吞掉。成功结论仍需展示其来源与适用条件。

## 5 接口与数据约束

现有入口为 `POST /api/v1/agent/query`；此前交接信息中的响应顶层字段包括 `intent`、`status`、`answer`、`structured_data`、`provenance`、`warnings`。这些是**对接线索**，队友必须先从仓库中的 schema、真实响应和示例请求核实嵌套结构、状态枚举和必填项，再提交字段映射表。不能依据本文件猜测字段值或自行改变接口。

前端只负责输入交互、状态管理、格式化和展示。BOM 展开、单位换算、齐套、缺料、风险、产能和采购数量都必须取自后端事实与计算结果。缺值不可默认填 0；不允许在前端用静态结果伪装正式响应。演示用 mock 应集中管理并醒目标注，只用于独立设计预览，接入真实接口后可关闭。

对来源数据设置统一视图模型：结论、指标、明细、引用、告警各自对应原始 API 路径。映射失败应显示可诊断的空态并记录开发日志，不应给用户展示错误结论。

## 6 视觉与交互要求

采用专业、克制的企业 SaaS 视觉语言，突出文字层级、数据表格和结论。桌面端以 1440 像素宽为主要展示场景，同时适配常见笔记本和手机；提供键盘可操作的输入、足够对比度、清晰的焦点与加载反馈。颜色不能成为区分风险的唯一方式。中文文案自然、简洁，不把内部节点名或原始 JSON 当作用户界面。

设计稿至少包含：首页、工作台、生产成功、生产受阻、库存查询、BOM 层级、产能限制、无数据、请求失败、窄屏布局。每种状态要写出示例内容及其数据来源类型，便于后续验收。

## 7 协作方式与代码边界

先提交信息架构、关键页面设计稿和交互说明，再编码。交付代码只在独立前端分支开发，修改范围限定于 `frontend/`。不修改 `api/`、`services/`、`agents/`、`tools/`、`workflows/`、`fact_layer/` 或数据库和原始数据，不改接口契约。不要在旧 `Chat.vue` 中持续堆条件分支；提取可复用的消息、结果、来源、警告、空态和 API 适配组件。保留已有可用的功能与构建配置。

若仓库中实际字段、能力或构建方式与本文件有出入，先在“待确认问题”中列明，并据真实代码修订对接方案；不擅自改后端。设计方案应能被另一个开发者依据交付材料接入。

## 8 交付清单与验收

交付以下内容：

1. 页面设计稿或可访问的原型，以及桌面端和窄屏端关键截图。
2. 可运行的 Vue 3 前端源码、运行说明和构建结果。
3. 页面结构图、组件清单与主要交互说明。
4. API 字段映射表，包含请求、响应、空值、告警和来源的真实样例。
5. mock 与真实接口的切换说明，以及未来版本能力的标注方式。
6. 测试说明：至少现场演示生产分析、事实查询、产能、无数据、接口失败和来源展开；记录每项结果。
7. 修改文件清单、已知限制和需要后端确认的问题。

**验收标准：** 新用户能从首页进入工作台并完成一条真实可复现的查询；结果与后端响应一致；无数据不被当成 0；结论能追溯来源；窄屏可用；前端构建通过；既有功能没有明显回退。未实现的路线图功能有明确标识，不冒充当前能力。
